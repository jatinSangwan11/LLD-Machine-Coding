# Stock Exchange — Current Attempt

Refined: 2026-11-02. This scope supersedes the file-input and multi-stock
requirements of the original interview brief for this attempt only.

## Objective and boundary

Implement an in-memory OrderMatchingEngine for one stock. A caller submits one
Order at a time through submit_order(order). No text-file input or CLI is needed.
Use Python. Process submissions sequentially; concurrency is out of scope.

## Input contract

Each Order supplies a unique order_id, side (buy/bid or sell/ask), exact price,
and positive integer quantity. Stock is fixed for this engine. For this attempt,
assume valid input and unique IDs. All orders are limit orders. The engine's
submission order defines time priority; supplied timestamps, if retained, are
informational and cannot reorder already processed arrivals.

## Functional requirements

1. Retain pending bids and asks for the one stock.
2. Attempt all eligible matches immediately upon submission, before accepting
   the next order.
3. A match requires buy price >= sell price, including equality.
4. Incoming buys take the lowest eligible ask first; incoming sells take the
   highest eligible bid first. Equal-price orders match FIFO by submission.
5. Execute min(buy remaining quantity, sell remaining quantity) shares per match.
6. Every execution uses the sell order's limit price, including incoming sells.
7. Remove fully filled orders. Partially filled resting orders retain their
   original priority; any incoming remainder becomes pending.
8. Never match same-side orders or aggregate separate executions into one trade.

## Output contract proposed for confirmation

submit_order returns the trades generated by that submission, in execution
order. Each trade contains buy_order_id, sell_price, quantity, sell_order_id.
Return an empty collection if there is no match. No direct printing is required.
This return contract is a refinement to confirm, not an earlier learner decision.

## Performance and scope

Aim for efficient best-price access and order insertion/removal; explain actual
complexities after choosing the design. No O(1) guarantee for a complete
submission: executing k trades requires at least O(k) work. Keep pending state
proportional to outstanding orders and any chosen price-group representation.
Use exact monetary arithmetic. No cancellations, amendments, market orders,
fees, persistence, inventory ownership checks, networking, or multi-stock routing.
Data structures and implementation remain learner decisions.
